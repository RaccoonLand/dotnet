# 10. RequestMetadata

`RequestMetadata` captures the immutable structural facts about a request type — the CLR types and the
pipeline kind — so that middleware never has to walk the request's interfaces at request time.

- **Package:** `RaccoonLand.Core.RequestProcessing.Abstractions`
- **Namespace:** `RaccoonLand.Core.RequestProcessing.Abstractions.Pipeline`

## Surface

```csharp
public sealed record RequestMetadata
{
    public RequestMetadata(Type requestType, Type? responseType, RequestKind kind);

    public Type RequestType { get; }        // concrete request CLR type
    public Type? ResponseType { get; }      // TResponse from IRequest<TResponse>; null for void IRequest
    public RequestKind Kind { get; }        // Command / Query

    public static RequestMetadata For(Type requestType, RequestKind kind);
}
```

| Member | Description |
| --- | --- |
| `RequestType` | The concrete CLR type of the request. |
| `ResponseType` | The `TResponse` from `IRequest<TResponse>`, or `null` for a void `IRequest`. Middleware that only applies to typed responses (e.g. caching, response mapping) checks `ResponseType is not null` and early-returns otherwise. |
| `Kind` | Whether the request flows through the command or the query pipeline. |
| `For(requestType, kind)` | Static memoized factory — resolves `ResponseType` via a single `IRequest<TResponse>` interface walk and caches the result in a process-wide `ConcurrentDictionary` keyed by `(Type, RequestKind)`. |

## Where metadata comes from

The dispatcher owns the metadata. When `AddRaccoonLandRequestProcessing` scans assemblies for endpoints, the
`EndpointInvokerRegistry` records a `RequestMetadata` per registered request type at the same time it captures
the invoker delegate. At dispatch time `RequestDispatcher` reads the pre-built metadata from the registry
(`ResolveMetadata(Type)`) and passes it to the `PipelineContext` — a single dictionary lookup, no reflection.

Middleware then consumes it cheaply:

```csharp
public Task InvokeAsync(PipelineContext context, PipelineDelegate next)
{
    if (context.Metadata.ResponseType is not { } responseType)
    {
        // Void request — nothing to cache, deserialize, or map.
        return next(context);
    }

    // …work with responseType…
}
```

## The `For(...)` helper

Production code should not need to call `For` — the dispatcher does the work once at startup. `For` exists for
two other cases:

- **Test authors** who construct a `PipelineContext` by hand to exercise a middleware in isolation.
- **Late-bound dispatchers** that route requests whose type was not present at scan time (dynamic plugins).

Both call sites are dwarfed by the request rate of the pipeline itself, but even here the memoized cache means
repeated resolutions of the same `(Type, Kind)` pair are O(1) and allocation-free:

```csharp
var metadata = RequestMetadata.For(typeof(MyQuery), RequestKind.Query);
var context = new PipelineContext(new MyQuery(), serviceProvider, metadata);
```

## Design notes

- The record is intentionally minimal today. It is designed to grow: attribute snapshots, `IsCacheable`,
  `HasValidator`, `RequiresAuthorization`, etc. can be added later without breaking consumers.
- `Kind` is part of the memoization key because the same request type could, in principle, be routed through
  either pipeline depending on host wiring. Keeping it in the key avoids aliasing bugs.
- `PipelineContext` validates at construction that `metadata.RequestType.IsInstanceOfType(request)`, so a
  middleware that reads `context.Metadata` can safely trust it.
